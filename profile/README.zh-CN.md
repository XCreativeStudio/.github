## 我们相信

**产品从一个问题开始，而不是一个点子。**
写第一行代码之前，我们得能把这句填完：「今天，____ 每次 ____ 的时候，只能用 ____ 的笨办法，代价是 ____。」填不出具体的人、具体的时刻，那就还没有产品，只有一个想法。点子会为了好用而变形，问题不会——这种不变形，正是它值钱的地方。

**值得解决的问题，应该让某件事真的变好，而不是变得更忙。**
标准不是「有人会点」，而是「如果它真做成了，有没有什么东西不一样了」。一个每天两次、每次省下九十秒麻烦的工具，够格。一个存在的意义是被欣赏的仪表盘，不够格。大多数软件都悄悄死在这条标准上，再怎么打磨也救不回来。

**爱上问题，把解决方案当消耗品。**
方案本来就该被重写：第一版是假设，不是祖传家产。不能动的只有问题本身。我们最警惕的是那种悄无声息的漂移——方案走不通了，于是把问题重新定义成一个更好卖的问题。产品就是这样丢掉它存在的理由的。

**做难而正确的事——因为正确，不是因为难。**
难不是美德，「我们很苦」也不是护城河。但一旦你知道正确答案是什么，它几乎总是比那个诱人的答案更贵：该做而不想做的迁移、没人愿意穷举的边界情况、漂亮功能之前必须先立起来的基础设施。捷径不会消失，它只是被存进代码库里，等下一个人来取。

**小，是决定，不是阶段。**
我们做小工具，不是把它当作通往大事的中转站。一个把一件事做完整的工具，是成品，不是原型。功能膨胀通常不是野心，是不肯决定「不为什么人做」。

**隐私是架构，不是一页政策。**
保护数据唯一可靠的办法，是不拥有它。能在你浏览器里算完的，就在你浏览器里算完——不上传、不注册、不需要你相信我们会好好保管。承诺善待数据，永远弱于根本不需要数据。

**发布，才知道；然后继续发布。**
关于用户想要什么，观点是免费的，而且通常是错的——包括我们自己的。一次发布，是买到证据最便宜的方式。所以第一版要小到有点难为情，第二版要回答一个具体问题。

## 怎么建

TypeScript · Vue / Nuxt · Node.js · Python。部署在 Vercel，小程序用微信云开发。

代码库要小，技术选型要「无聊」——是故意的。默认开源，除非有明确的理由不开。
